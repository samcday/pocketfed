## Current kernel experiment

The experiment adds a default-off, load-time module parameter:

`qseecomtee.reuse_invoke_pool=0` or `1`

With `0`, invocation staging retains the original behavior: create a fresh coherent TZ pool for each command and destroy it afterwards.

With `1`, staging uses the driver’s existing long-lived TZ memory pool. Individual allocations are still cleared and freed back to that pool. This retains the backing mappings across calls; it does **not** implement permanent command contents or a new application-owned buffer protocol.

The patch leaves request/response/auxiliary layout, copying, zeroing, secure calls and return handling intact. This is a controlled allocator/mapping comparison, not an established repair or an agreed long-term kernel design.

## Hypotheses: established facts versus open questions

- Repeated per-invoke coherent allocation/unmapping is present in the kernel, and a captured worker blocked in that allocation path. Whether it initiates the freeze, exposes an earlier fault, or is merely where synchronization notices an unresponsive CPU is unresolved.
- A trusted-app buffer-lifetime problem, mapping/cache interaction, or another secure-world/platform interaction remains possible. The persistent-pool experiment has not reached a sensor command yet and proves none of these explanations.
- The generic kernel bounce path places responses immediately after the request. That could matter for protocols requiring additional alignment, but these FPC sensor commands already use 64-byte requests and responses. The suspected general alignment issue does not explain these INIT/DEEP_SLEEP exchanges by itself.
- CPU pinning did not provide a workaround. The CPU-latency request did not produce a successful comparison either.
- BPF cleanup and RCU waits are observed consequences of cross-CPU nonresponse; no evidence establishes them as the initiating fault.
- Source-level inspection noticed possible A55/Kryo erratum coverage questions. No erratum patch was tested or justified as the cause. Do not promote that speculation into a diagnosis.
- Successful one-off initialization and five plain Claim/Release cycles were insufficient to establish reliability. Both earlier short tests and real desktop successes were followed by later freezes.

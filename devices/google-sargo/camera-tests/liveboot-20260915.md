
## GNOME Snapshot via PipeWire (15 September, evening)

The selected app path is GNOME Snapshot 51.beta on PipeWire's libcamera plugin,
the same stack postmarketOS and Mobian ship for Phosh. On fresh `.11` liveboots
with the CAMCC early-load profile (`sargo-camera-snapshot-0[123]-20260915`),
libcamera `4.fc46.native.2` (pinned IMX363 tuning), pipewire 1.6.8 and
wireplumber 0.5.14 run as root in a private runtime directory and publish the
rear sensor as a `Video/Source` node. [`snapshot-session/`](snapshot-session/README.md)
is the gated command; every finding below came from an actual run.

Accepted so far (trial 04, helper `e9ace8bd`, CPU software ISP):

- Snapshot saved a 1920x1080 JPEG after one `t` press, with EXIF orientation 8
  written by `jifmux` from the `pipewiresrc` rotation tag, so it displays
  upright (the viewfinder is upright too). `check-jpeg.py` decoded the exact
  QR payload; every graded line down to 10 pt is legible; swatch hues are right
  with a green cast. The target was shown on a monitor: the printed-page clause
  is still unmet by evidence. Manual focus: `focus_absolute=3072` on the
  LC898219XI, chosen by a gated PipeWire focus sweep (sharpness peaks there for
  the target at about 30 cm). The strict release gate passed before and after.

What it took, in the order the runs exposed it:

1. A private session bus auto-activated `xdg-desktop-portal`; Snapshot then
   took the portal camera route and this WirePlumber grants that remote no
   node ("no camera found"). With no bus at all Snapshot parked on its startup
   spinner. The helper now starts a `dbus-daemon` that cannot activate
   services (`--private-bus`).
2. Snapshot enumerated the front IMX355 first, and libcamera inside WirePlumber
   failed its DMA-heap allocation on a CMA heap. The helper disables the front
   node through a WirePlumber rule and runs WirePlumber with only the system
   heap visible, like `cam-system-heap`.
3. Snapshot starts its camera only once its window is *active*
   (`connect_is_active_notify`). Foreign-toplevel activation is accepted by
   Phoc but does not make the window active; a uinput pointer click through
   libinput does (`ydotoold`/`ydotool`), which is what a finger did in the runs
   that streamed.
4. Snapshot's `take_picture` disables `win.take-picture` before its readiness
   check, so one early press leaves the shutter dead; the helper waits for the
   PipeWire node state `running` before the lens write and the first press.
5. Writing the lens while the camera is idle fails its power-on ("LSI wake up
   check failed") and leaves the driver in a runtime-PM error that only a
   reboot clears. The lens is set only after the stream runs.

Open (trial 05): repeated capture fails. camerabin accepts the second
`start-capture`, but `pipewiresrc` logs `buffer ... was not recycled` from the
first seconds and the stream stops delivering frames about 19 s in, so the
second capture never starts and Snapshot stays in "Operation in progress".
Upstream pipewire fixed this after 1.6.8 (`gstpipewiresrc: copy the last free
buffer instead of stalling the stream`, plus a lock-order fix); a
`pipewire-gstreamer` rebuild with those two commits is being tried. Close and
reopen is unverified until repeated capture works. The GPU software-ISP path
remains unused pending the `native.5` libcamera candidate, which carries the
centred statistics-window fix for its top-left-corner metering.

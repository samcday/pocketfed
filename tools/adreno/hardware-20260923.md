# A3xx hardware controls, 2026-09-23

Follow-up to [Rob Clark's requests](https://gitlab.freedesktop.org/mesa/mesa/-/work_items/12634#note_3674373)
and the [host evidence audit](rob-followup.md). This is an ongoing experiment,
not a production Mesa fix. New results below use the prepared Fedora 46
Mesa 26.2.2 libraries on DB410c/A306 with Fedora 7.3-rc3. B1–B8 use its unchanged MSM module; B9 tests the
separately identified recovery candidate.

## First boot: minimal clear + draw

All four runs use the same reduced trace and display session, with shader cache
disabled. The guest verified every payload checksum. Both `ldd -r` and the
running retracer's maps identify the intended override; captured environment
confirms the chosen `FD_MESA_DEBUG`. Scanout was active before the trials.

| Trial | Library | Mode | GPU result (retired/submitted fences) | GPU clock reference counts |
| --- | --- | --- | --- | --- |
| t01 | stock | sysmem,flush | No hang; fences 943/943 | unchanged |
| t02 | direct-wait | sysmem | No hang; fences 961/961 | unchanged |
| t03 | direct-no-wait | sysmem | No hang; fences 979/979 | unchanged |
| t04 | wait-only | sysmem | Hang; fences 991/994, then recovery | all six GPU-owned clocks +1 |

The direct arms contain no per-upload logging. Neither passing arm caused a
hangcheck; final RBBM status was `0x1`, ring pointers matched, and the same
compositor remained alive. These are replay/completion checks, not pixel or
performance claims. Reported frame timings include compilation and setup.

Wait-only still returned process exit 0 after recovery; it is **not a pass**.
At uptime 353.776 s the kernel detected a lockup, recovered at 353.798 s, and
reported a ring-drain timeout at 354.870 s with RPTR 0 / WPTR `0x1726`.
The compositor then crashed with SIGSEGV. Final fences 994/994 establish
retirement after recovery, not an intact rendering session.

This gives a narrow answer to the CPU-prep question: adding B2's prep call to
the unchanged indirect path was insufficient here, while the matched direct
path worked without that explicit call. Mapping/copying, command layout,
source visibility and timing remain distinct possible explanations.
The matched wait arms deliberately preserve B2's ignored prep return; these
runs establish behavior with that call present, not independently verified
successful prep. The error-checked follow-up also hangs without a reported
prep error; see B8.

The first new hardware dump is 94,243 bytes, SHA-256
`eeff1f07a9c91d5d67d65ce146a11eeeeb0c954f7dce9d487fedf5d7b222b69c`.
The host copy matches the guest hash. It reports RBBM `0xe0684003` and submitted/retired fences
994/991. Command BO `0x0348e000` still contains the expected indirect loads:

```text
+0x488: VS DST_OFF=16 NUM_UNIT=16, source=0x03a99240 (128 bytes)
+0x558: FS DST_OFF=16 NUM_UNIT=32, source=0x03a99240 (256 bytes)
```

All ten CP_LOAD_STATE packets decode without warnings. Raw logs and dumps stay
in ignored local artifacts.

## Second boot: full trace, pixels, and stock negative control

An orderly reboot restored baseline clock counts and a new display session.
Trials t05–t10 use the full `r3.trace`, disabled shader cache, and the same
verified library overrides and environment. All completed before any B2
hang/recovery; phoc PID 1109 and active scanout remained intact throughout them.

| Trial | Library | Mode | Replay | GPU result (retired/submitted fences) | GPU clock references |
| --- | --- | --- | --- | --- | --- |
| t05 | stock | sysmem,flush | Full trace, no readback | No hang; 993/993 | unchanged |
| t06 | direct-no-wait | sysmem | Full trace, no readback | No hang; 1011/1011 | unchanged |
| t07 | direct-wait | sysmem | Full trace, no readback | No hang; 1028/1028 | unchanged |
| t08 | stock | sysmem,flush | Full trace, PNG at call 6260 | No hang; 1061/1061 | unchanged |
| t09 | direct-no-wait | sysmem | Full trace, PNG at call 6260 | No hang; 1079/1079 | unchanged |
| t10 | direct-wait | sysmem | Full trace, PNG at call 6260 | No hang; 1098/1098 | unchanged |
| t11 | stock | sysmem | Minimal clear + draw | Hang; 1112/1115, then recovery | all six GPU-owned clocks +1 |

The three PNGs have identical decoded pixels and identical SHA-256:
`2d34c84ae83f9d0814880c0d062bf664572f191a93e6cb6beb02889ce8e36775`.
Host hashes match the guest hashes. All are 1280×688 with 653 RGB colors;
visual inspection shows the actual GTK gradient probe and its text, rather
than an empty frame. The local `hardware/pixels/comparison.json` records the
comparison. These establish equality to the stock+flush reference at this
captured frame, not general rendering correctness. Separate no-readback
trials t05–t07 establish that adding the snapshot was not required for those
completion results.

The stock indirect negative control t11 used the minimal trace without
`flush`. It hung at uptime 711.728 s, recovered at 711.750 s, and reported the
same post-reset drain failure at 712.822 s, this time RPTR 0 / WPTR `0x1EBC`.
It returned exit 0 and eventually retired fence 1115, but phoc PID 1109 crashed
with SIGSEGV at 713.687 s. The AFTER display check showed active scanout and a
replacement phoc PID 3213: this was a crash/restart, not an intact session.

Together with the first boot, this extends the direct-no-wait result to the
full trace and matching captured pixels. The added explicit CPU-prep call is
not required for those observed direct-upload passes, and adding it to the
indirect path did not prevent the minimal-trace hang. These CPU-initialized
trace results still leave source visibility, copying, packet layout and timing
as possible explanations; they do not establish behavior for GPU-produced
constant data.

## Third boot: fresh-source indirect

Trial t12 used `fresh-source + sysmem` on the same minimal trace, from a new
boot with baseline clocks. The library hash, runtime maps and environment
match the prepared control; no `FD3FRESH` fallback was logged. It hung at
162.738 s with retired/submitted fences 1907/1908, recovered at 162.760 s,
then timed out draining RPTR/WPTR `0/180E` at 163.826 s. All six GPU clock
enable/prepare counts increased by one. phoc PID 1059 crashed with SIGSEGV at
165.950 s and was absent from the final process check. Exit 0 is again not a
passing result.

The 95,883-byte devcoredump has SHA-256
`ccb5bcd3f62f84b96d495854ad7ff0275529f19ef7248ddca80cfa32f4ddda73`.
It reports the same RBBM `0xe0684003`, with the two indirect loads unchanged
in size and source offset: VS 128 bytes from `0x02cd4240`, FS 256 bytes from
`0x02cd8240`. These reference distinct 16-KiB source BOs at `0x02cd4000` and
`0x02cd8000`. Their captured contents, reconstructed with the zero tails
trimmed by the kernel dump writer, are byte-identical. The original UBO lacks
captured data, so this dump cannot independently prove original-to-copy
equality or what the GPU saw through its caches. The captured 13,792-byte FS
again matches the host p7/B10 shader byte-for-byte.

The saved ring has RPTR=WPTR=6158, unlike the earlier stock/wait snapshots;
this is a hang with fresh captured sources, not proof of an identical stall
point. The later printed fence equality is the recovery worker's software
fence advance, not evidence of intervening GPU progress.

## Assertion-enabled scheduler comparison: B5 and B6

After the B4 boot failure, a physical reset and new root-server process allowed
both trials to boot normally. Each used the same eight-arm root with all eleven
payload checksums verified, the stock loaded module, active scanout and a healthy
compositor before replay. The O2/assertions-on pair differs only by the two
!44620 commits. Runtime maps, environment and loader checks identify the intended
library; shader cache was disabled and both used the minimal trace in sysmem.

| Boot / trial | Library | GPU result (retired/submitted) | Assertion | Compositor |
| --- | --- | --- | --- | --- |
| B5 / t13 | stock-asserts | Hang at 223.729 s; 2007/2010 | No failure | phoc 1065 SIGSEGV at 226.111 s |
| B6 / t14 | sched | Hang at 389.743 s; 1220/1223 | No failure | phoc 1055 SIGSEGV at 392.226 s |

Both retracers returned exit 0 after recovery, and both increased all six GPU
clock enable/prepare counts by one. The MR therefore does not fix this GTK
minimal reproducer. Both captured fragment shaders are byte-identical to each
other and to the earlier host/hardware shader: 13,792 bytes, SHA-256
`6b277e86d377c9497a3d6c9c8fc55fa9300627c937d42b8ef68907f12f19d788`.
The unchanged VS/FS indirect loads request 128/256 bytes from source offset 576.
This shader has no kill/discard/demote and does not exercise the specific
cross-block kill/bary.f condition; these results do not evaluate that condition
or SuperTuxKart shaders.

Guest-hash-verified devcoredumps:

- t13: 94,277 bytes, `62e36db7c55291ae29a5737da34e7537d762ba6cf6100675846c1de70e91b2e1`.
- t14: 94,276 bytes, `c6f9b6d53427e8971981b510322bab864eb27571115ed8ebec50db14b89dd8e8`.

Both runs used the scoped return-tracing helper. The recovery GPU-worker's
`a3xx_pm_suspend()` returned `-16` (`-EBUSY`) to `adreno_recover+0x34`, followed
by `msm_gpu_pm_resume()` returning 0 to `adreno_recover+0x44`. Generic suspend
was never called. There were zero missed probes and zero per-CPU buffer
overruns or dropped events. Other `-EBUSY` returns came from normal runtime
suspend; the recovery pair is distinguished by its caller/task. The return
sequence directly confirms the previously inferred recovery mechanism.

Trials t04, t11, t12, t13, t14 and t15 reproduced
the same change from their own fresh-boot baseline. Before and after each trial, GPU runtime status
was active with `power/control=auto` and runtime suspended time zero. The
following enable **and** prepare counts changed together after each recovery:

| Clock | Before | After |
| --- | ---: | ---: |
| gcc_oxili_gfx3d_clk | 1 | 2 |
| gcc_oxili_gmem_clk | 1 | 2 |
| gcc_oxili_ahb_clk | 1 | 2 |

| gcc_bimc_gpu_clk | 1 | 2 |
| gfx3d_clk_src | 3 | 4 |

The IOMMU clocks and `bimc_gpu_clk_src` parent counts did not change; rates stayed
unchanged. All six GPU references were stable through the non-hanging B2
controls t05–t10. The B5/B6/B8 callback traces directly confirm the
[failed-suspend/unconditional-resume mechanism](recovery-clocks.md) identified
in source and Fedora's shipped module. This is evidence about recovery, not the
cause of the original hang, and runtime suspended time does not count direct recovery callbacks.

The separate [draft kernel correction](https://github.com/samcday/linux/pull/5)
uses generic suspend during A3xx recovery after software reset, preserving
normal runtime-suspend idle/VBIF checks and the resume/hardware-init sequence.
Apply/whitespace/checkpatch checks pass. The three affected ARM64 translation
units (`adreno_gpu.o`, `a3xx_gpu.o`, `msm_gpu.o`) also compile against the exact
upstream base with upstream arm64 defconfig; logs/config/compiler provenance
are archived under `out/adreno-rob-20260923/recovery-evidence/kernel-cross-compile/`.
A separate complete `msm.ko` build now passes with the exact shipped Fedora
configuration, generated headers and symbol table, using its matching ARM64
compiler/linker. Its vermagic, 784 imports and ten dependencies match stock;
the Fedora source RPM comparison and emitted recovery branch were checked.
The CRC32-XZ candidate has SHA-256
`f128ed08e25e826e6c714c1a3aa2e718d1450f3e63356d05c4bc8cfe0ab7bfe1` and build ID
`8781436f3c1601233e20bdb11e67be06244fe222`. Evidence is under
`out/adreno-rob-20260923/recovery-evidence/fedora-module/`. This unsigned
external module lacks module BTF; static compatibility checks do not establish
loadability or recovery behavior. B9 below now verifies the loaded candidate
and its first recovery; broader coverage is recorded separately.

B4 failed during boot with ext4 inode-checksum errors before `/sbin/init`; no scheduler trial

## B8: checked-wait also hangs without a reported prep failure

A physical reset and fresh root-server process restored a healthy boot. The
stock loaded-module note and all eleven payload checksums matched; phoc PID
1029 had active scanout. `ldd -r`, runtime maps, library hash and environment
identify the matched release/O3 `wait-checked` arm in sysmem, with cache disabled.

Trial t15 hung at 221.744 s with retired/submitted fences 1875/1878. It emitted
no `FD3WAIT_CHECK` preparation error and did not abort: the process returned 0
after recovery. This diagnostic propagates existing fence-wait errors and
aborts on a nonzero prep result before the unchanged indirect emission. Thus
this run does not hide a reported preparation failure. Zero still permits an
already-idle fast path; it does not prove that a blocking wait occurred.

Recovery at 221.766 s was followed by the drain timeout at 222.838 s, RPTR/WPTR
`0/15EA`, and phoc SIGSEGV at 223.884 s. All six GPU clock enable/prepare counts
increased by one. The `gfx3d_clk_src` AFTER line was interrupted by an audit
message after its counts/rate; a separate compact read confirmed 4/4 and the
unchanged rate. Neighboring comparison-clock counts/rates remained unchanged.
The scoped trace again records recovery suspend `-EBUSY`, resume 0, no generic
suspend, zero missed probes and zero per-CPU buffer loss. Scoped cleanup passed.

The guest-hash-verified dump is 94,277 bytes, SHA-256
`e4223653e4b868704c24be2742cbab10aef2125c58bf570f274d771a663232c3`.
It reports RBBM `0xe0684003`, saved RPTR/WPTR 5600/5610, and unchanged VS/FS
indirect loads of 128/256 bytes from UBO+576. The 13,792-byte FS is byte-identical
to the stock t11 shader. The original source UBO has no captured payload.

## B9: candidate recovery module and rendering after recovery

The temporary boot preserves the same root image, kernel Image and DTB and
changes only the initramfs MSM module. Its live module-note SHA-256 is
`26a44dfeccef1cc8b948b6a68983334760c61831783faae4a907aa37e8cad56b`, matching the
built candidate. Fedora accepts the unsigned external module with taint 12288.
All eleven payload hashes, loader checks, active scanout and phoc PID 1083 were
verified before the first trial.

Stock/sysmem minimal trial t16 still hangs at 239.727 s (retired/submitted
1456/1459), with recovery at 239.750 s. The candidate directly calls generic
suspend and resume, both returning 0 to `adreno_recover`; its A3xx suspend
callback is not called by recovery, and no stale-ring drain timeout appears.
All six GPU clock enable/prepare counts remain at their fresh-boot baselines.
The scoped capture has zero missed probes and zero per-CPU buffer losses;
cleanup succeeds. Normal runtime-suspend failures in the same capture have
distinct `adreno_runtime_suspend` callers.

The Mesa hang and compositor failure remain: phoc 1083 crashes with SIGSEGV
at 241.166 s. The display-manager alias resolves to `phrog.service`, which
automatically starts a replacement phoc PID 2674. This is recovery of the
service, not survival of the original display session.

After confirming that replacement's active scanout, t17 replays full R3 with
stock Mesa and `sysmem,flush`. It completes with fences 2170/2170, unchanged
clocks and the same replacement compositor. Its 1280×688 PNG at call 6260 is
byte-identical to the preexisting t08 reference (SHA-256
`2d34c84ae83f9d0814880c0d062bf664572f191a93e6cb6beb02889ce8e36775`). This
establishes rendering after recovery/service restart at that captured frame.

The t16 devcoredump is 94,276 bytes, SHA-256
`5f9ff65e5fcfd0b7585882087875c11ab5347a0ca2815490bc6b538893294914`.
It retains RBBM `0xe0684003`, RPTR/WPTR 6246/6260, and VS/FS indirect loads of
128/256 bytes from UBO+576. The dump, return-trace directory and t17 PNG were
transferred and verified against guest hashes before further trials.

A second deliberate stock/sysmem minimal hang, t18, occurs at 491.759 s with
fences 2185/2188, recovery at 491.782 s and phoc 2674 SIGSEGV at 492.474 s.
Both generic recovery calls again return 0, there is no stale-ring timeout,
and all six clock counts remain balanced. This capture also has zero missed

was hash-checked and acknowledged before t18, so the new dump is distinct:

`5b8ba94d6b1f10693b6b0bcd4844b7c19b4d600919452badba4369405c042898`.
Both candidate-run fragment shaders match each other and the prior stock FS.

The subsequent ordinary runtime-PM check t19 stops `phrog.service` and confirms

suspend returns `-EBUSY`; runtime status stays active, suspended time stays

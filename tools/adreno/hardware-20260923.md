# A3xx hardware controls, 2026-09-23

Follow-up to [Rob Clark's requests](https://gitlab.freedesktop.org/mesa/mesa/-/work_items/12634#note_3674373)
and the [host evidence audit](rob-followup.md). This is an ongoing experiment,
not a production Mesa fix. New results below use the prepared Fedora 46
Mesa 26.2.2 libraries on DB410c/A306 with Fedora 7.3-rc3. B1–B8 and B10 use its unchanged MSM module; B9 tests the
separately identified recovery candidate. B11 uses the mask-only correction,
B12 combines recovery and mask corrections, and B13 adds the initialization guard.

## First boot: minimal clear + draw

All four runs use the same reduced trace and display session, with shader cache
disabled. The guest verified every payload checksum. Both `ldd -r` and the
running retracer's maps identify the intended override; captured environment
confirms the chosen `FD_MESA_DEBUG`. Scanout was active before the trials.

| Trial | Library | Mode | GPU result (retired/submitted fences) | GPU clock reference counts |
| --- | --- | --- | --- | --- |
| t01 | stock | sysmem,flush | No hang; fences 943/943 | unchanged |
| t02 | direct-wait | sysmem | No hang; fences 961/961 | unchanged |
| t03 | direct-no-wait | sysmem | No hang; fences 979/979 | unchanged |
| t04 | wait-only | sysmem | Hang; fences 991/994, then recovery | all six GPU-owned clocks +1 |

The direct arms contain no per-upload logging. Neither passing arm caused a
hangcheck; final RBBM status was `0x1`, ring pointers matched, and the same
compositor remained alive. These are replay/completion checks, not pixel or
performance claims. Reported frame timings include compilation and setup.

Wait-only still returned process exit 0 after recovery; it is **not a pass**.
At uptime 353.776 s the kernel detected a lockup, recovered at 353.798 s, and
reported a ring-drain timeout at 354.870 s with RPTR 0 / WPTR `0x1726`.
The compositor then crashed with SIGSEGV. Final fences 994/994 establish
retirement after recovery, not an intact rendering session.

This gives a narrow answer to the CPU-prep question: adding B2's prep call to
the unchanged indirect path was insufficient here, while the matched direct
path worked without that explicit call. Mapping/copying, command layout,
source visibility and timing remain distinct possible explanations.
The matched wait arms deliberately preserve B2's ignored prep return; these
runs establish behavior with that call present, not independently verified
successful prep. The error-checked follow-up also hangs without a reported
prep error; see B8.

The first new hardware dump is 94,243 bytes, SHA-256
`eeff1f07a9c91d5d67d65ce146a11eeeeb0c954f7dce9d487fedf5d7b222b69c`.

## B10: clean stock idle failure and A306 halt-mask mismatch

and suspended time stays zero. The earlier service stop alone produced no traced
callback; the failed attempt is identified by the explicit policy markers.

Trial t21 places a read-only, stock-binary-specific kprobe immediately before
the driver clears the VBIF request. A second on/auto attempt records:

```text
539.656022 a3xx_pm_suspend+0xb4: poll_ret=-110 request=0x7 ack=0x70007
539.656038 a3xx_pm_suspend -> adreno_runtime_suspend+0x44: ret=-16
```

separate from the recovery clock imbalance. The [A306 mask correction](https://github.com/samcday/linux/pull/6)
is under test; it leaves other A3xx masks unchanged. See the
[probe/source audit](vbif-halt.md) and [guarded helper](trace-vbif-halt.sh).

Both captures have zero missed probes and zero per-CPU overruns/dropped events;
scoped cleanup succeeds. Guest-hash-verified archives:

- t21: `ab65466ed1fd3da5e38aca7966e9b15310035e006235ce85ba93d1081723d958`

The display service is restored (phoc 2361 active) before an orderly reboot.

## Diagnostic review follow-up

Review identified that interrupting a helper's separate `stop` invocation
could leave its probes registered. All three published helpers now install
stop-path EXIT/INT/TERM cleanup traps, preserve the original exit status and
mark interrupted/incomplete captures explicitly. [Local process tests](tests/test-stop-cleanup.py)
exercise normal stop, real SIGINT/SIGTERM during a blocked FIFO read, and a
cleanup failure while interrupted: all 12 cases pass. These test the stop
control flow with a mocked teardown, without touching tracefs or devices.
Bash syntax and ShellCheck also pass. Hardware captures above precede this
stop-trap robustness change; their normal scoped cleanup already succeeded.
The VBIF audit now correctly calls the five configured probes "probes," as
the two generic callbacks had no hits in the stock localization test.

### Result

**Named change:** emit `CP_EVENT_WRITE HLSQ_FLUSH` immediately before every
`CP_LOAD_STATE` of constants with `SS_INDIRECT` (fixI). Indirect loads remain in
the stream (host-verified). Without it the minimal pair hangs (t31, t32, t52 and
every hanging control); with it the minimal pair passes 3/3 (t57, t60b, t61b),
the full trace renders bit-identical frames in sysmem and default GMEM (t63b,
t64b = reference `2d34c84a…`), the #82 probe completes 450/450 without faults
(g6x-fixI), Settings survives six panel switches (st68), and STK completes twice
(s72, s78) where stock, Patch A and fixL reset the SoC.

**Where the separator must sit (minimal pair):** every element placed directly
before the FS indirect load that contains an `HLSQ_FLUSH` or a `CP_WAIT_FOR_IDLE`
avoids the hang (t49 `hlsq`, t48 `wfi`; t46 `epi`, t47 `inv` and t50 `uche` each
include one of them). In the hanging stream that load (destination offset 16,
32 units) directly follows the FS direct upload (offset 0), while the flush that
stock `fd3_emit_state()` emits before all constant uploads, and the WFI from
`ring_wfi()`, precede the VS indirect load. The same events do
not help after the VS indirect load (t54), before it (t51), between the VS and FS
uploads (t53, t58, t59b), at the start of the draw (t34, t35, t39), or after
the previous draw (t40), and neither does a new IB at the draw (t41). A full
`fd3_emit_restore()` plus re-emitting all state avoids it (t33); the restore
packets without its register block do not (t39). The hang also needs the VS
indirect load in the same draw (t55: VS constants inline → pass). In every
hanging variant another draw precedes the rounded-clip draw in the same submit,
and it need not be the clear (t44, t45); no single-draw control was run in this
series. Forcing the passing clip-none VS into CACHE mode does not make it hang
(t43).

**Limitations:** one board (A306 `03000600`), Fedora 7.3-rc3 with the all-three
MSM candidate, Mesa 26.2.2 backports of the change; the Mesa-main patch is
host-verified (build, clang-format on the hunk, drm-shim diff) but was not run on
hardware. The mechanism inside HLSQ is inferred from these placements, not from
documentation. STK was run without the compositor (KMS) because of RAM.

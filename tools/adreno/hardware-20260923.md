# A3xx hardware controls, 2026-09-23

Follow-up to [Rob Clark's requests](https://gitlab.freedesktop.org/mesa/mesa/-/work_items/12634#note_3674373)
and the [host evidence audit](rob-followup.md). This is an ongoing experiment,
not a production Mesa fix. New results below use the prepared Fedora 46
Mesa 26.2.2 libraries on DB410c/A306 with the unchanged Fedora 7.3-rc3 kernel.

## First boot: minimal clear + draw

All four runs use the same reduced trace and display session, with shader cache
disabled. The guest verified every payload checksum. Both `ldd -r` and the
running retracer's maps identify the intended override; captured environment
confirms the chosen `FD_MESA_DEBUG`. Scanout was active before the trials.

| Trial | Library | Mode | GPU result (retired/submitted fences) | GPU clock reference counts |
| --- | --- | --- | --- | --- |
| t01 | stock | sysmem,flush | No hang; fences 943/943 | unchanged |
| t02 | direct-wait | sysmem | No hang; fences 961/961 | unchanged |
| t03 | direct-no-wait | sysmem | No hang; fences 979/979 | unchanged |
| t04 | wait-only | sysmem | Hang; fences 991/994, then recovery | all six GPU-owned clocks +1 |

The direct arms contain no per-upload logging. Neither passing arm caused a
hangcheck; final RBBM status was `0x1`, ring pointers matched, and the same
compositor remained alive. These are replay/completion checks, not pixel or
performance claims. Reported frame timings include compilation and setup.

Wait-only still returned process exit 0 after recovery; it is **not a pass**.
At uptime 353.776 s the kernel detected a lockup, recovered at 353.798 s, and
reported a ring-drain timeout at 354.870 s with RPTR 0 / WPTR `0x1726`.
The compositor then crashed with SIGSEGV. Final fences 994/994 establish
retirement after recovery, not an intact rendering session.

This gives a narrow answer to the CPU-prep question: adding B2's prep call to
the unchanged indirect path was insufficient here, while the matched direct
path worked without that explicit call. Mapping/copying, command layout,
source visibility and timing remain distinct possible explanations.

The first new hardware dump is 94,243 bytes, SHA-256
`eeff1f07a9c91d5d67d65ce146a11eeeeb0c954f7dce9d487fedf5d7b222b69c`.
The host copy matches the guest hash. It reports RBBM `0xe0684003` and submitted/retired fences
994/991. Command BO `0x0348e000` still contains the expected indirect loads:

```text
+0x488: VS DST_OFF=16 NUM_UNIT=16, source=0x03a99240 (128 bytes)
+0x558: FS DST_OFF=16 NUM_UNIT=32, source=0x03a99240 (256 bytes)
```

All ten CP_LOAD_STATE packets decode without warnings. Raw logs and dumps stay
in ignored local artifacts.

## Second boot: full trace, pixels, and stock negative control

An orderly reboot restored baseline clock counts and a new display session.
Trials t05–t10 use the full `r3.trace`, disabled shader cache, and the same
verified library overrides and environment. All completed before any B2
hang/recovery; phoc PID 1109 and active scanout remained intact throughout them.

| Trial | Library | Mode | Replay | GPU result (retired/submitted fences) | GPU clock references |
| --- | --- | --- | --- | --- | --- |
| t05 | stock | sysmem,flush | Full trace, no readback | No hang; 993/993 | unchanged |
| t06 | direct-no-wait | sysmem | Full trace, no readback | No hang; 1011/1011 | unchanged |
| t07 | direct-wait | sysmem | Full trace, no readback | No hang; 1028/1028 | unchanged |
| t08 | stock | sysmem,flush | Full trace, PNG at call 6260 | No hang; 1061/1061 | unchanged |
| t09 | direct-no-wait | sysmem | Full trace, PNG at call 6260 | No hang; 1079/1079 | unchanged |
| t10 | direct-wait | sysmem | Full trace, PNG at call 6260 | No hang; 1098/1098 | unchanged |
| t11 | stock | sysmem | Minimal clear + draw | Hang; 1112/1115, then recovery | all six GPU-owned clocks +1 |

The three PNGs have identical decoded pixels and identical SHA-256:
`2d34c84ae83f9d0814880c0d062bf664572f191a93e6cb6beb02889ce8e36775`.
Host hashes match the guest hashes. All are 1280×688 with 653 RGB colors;
visual inspection shows the actual GTK gradient probe and its text, rather
than an empty frame. The local `hardware/pixels/comparison.json` records the
comparison. These establish equality to the stock+flush reference at this
captured frame, not general rendering correctness. Separate no-readback
trials t05–t07 establish that adding the snapshot was not required for those
completion results.

The stock indirect negative control t11 used the minimal trace without
`flush`. It hung at uptime 711.728 s, recovered at 711.750 s, and reported the
same post-reset drain failure at 712.822 s, this time RPTR 0 / WPTR `0x1EBC`.
It returned exit 0 and eventually retired fence 1115, but phoc PID 1109 crashed
with SIGSEGV at 713.687 s. The AFTER display check showed active scanout and a
replacement phoc PID 3213: this was a crash/restart, not an intact session.

Together with the first boot, this extends the direct-no-wait result to the
full trace and matching captured pixels. The added explicit CPU-prep call is
not required for those observed direct-upload passes, and adding it to the
indirect path did not prevent the minimal-trace hang. These CPU-initialized
trace results still leave source visibility, copying, packet layout and timing
as possible explanations; they do not establish behavior for GPU-produced
constant data.

## Recovery clock observation

Both t04 (wait-only, B1) and t11 (stock, B2) reproduced the same change from
their own fresh-boot baseline. Before and after each trial, GPU runtime status
was active with `power/control=auto` and runtime suspended time zero. The
following enable **and** prepare counts changed together after each recovery:

| Clock | Before | After |
| --- | ---: | ---: |
| gcc_oxili_gfx3d_clk | 1 | 2 |
| gcc_oxili_gmem_clk | 1 | 2 |
| gcc_oxili_ahb_clk | 1 | 2 |
| gcc_bimc_gfx_clk | 1 | 2 |
| gcc_bimc_gpu_clk | 1 | 2 |
| gfx3d_clk_src | 3 | 4 |

The IOMMU clocks and `bimc_gpu_clk_src` parent counts did not change; rates stayed
unchanged. All six GPU references were stable through the non-hanging B2
controls t05–t10. This repeated pattern strongly supports the
[failed-suspend/unconditional-resume hypothesis](recovery-clocks.md) identified
in source and Fedora's shipped module. The callback return itself was not
traced. This is evidence about recovery, not the cause of the original hang,
and runtime suspended time does not count direct recovery callbacks.

The separate [draft kernel correction](https://github.com/samcday/linux/pull/5)
uses generic suspend during A3xx recovery after software reset, preserving
normal runtime-suspend idle/VBIF checks and the resume/hardware-init sequence.
It has apply/whitespace/checkpatch validation only; no kernel build or patched
hardware result is claimed here.

Fresh-source indirect controls and the matched assertion-enabled scheduler
pair remain pending. Further comparisons need a fresh boot because t11 again
changed clock references and compositor state.

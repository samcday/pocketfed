# DB410c: direct U-Boot liveboot

The [DB410c epic](https://github.com/samcday/pocketfed/issues/79) describes an
older Pocketboot resident/kexec route. The September 22, 2026 trial instead
booted directly from U-Boot fastboot using the Fedora 7.3 kernel and prepared
initrd from [#81](https://github.com/samcday/pocketfed/pull/81), based on
[#75](https://github.com/samcday/pocketfed/pull/75).

Use `profiles/uboot-db410c.yaml` for this route. It matches U-Boot's `product=sbc`
and uses a plain Android v2 image with a separate DTB. The kernel must support
the board's PSCI firmware. A kernel built for the older resident/spin-table
handoff is a different input and is not validated by this trial.

## Reproduce with prepared inputs

Build this consumer with `cargo build --release --locked`. Obtain a matching
kernel bundle and smoo-aware dracut initrd using the #81/#75 recipe. The trial
used kernel `7.3.0-0.rc3.260918g5dd1818b15d9.36.fc46.aarch64`, its packaged
DB410c DTB, and a 23,526,504-byte prepared initrd. Its existing 8 GiB Phosh root
was the Sargo-derived Adreno lab image, including lab userspace payloads; this
was not a newly built DB410c image variant.

Create `cmdline.txt` using the actual deployment's `ostree=...` path and:

```text
rw
rd.smoo.cow.size=512M
console=ttyMSM0,115200n8
enforcing=0
video=HDMI-A-1:1280x720@60e
rd.smoo.product=0xBEE1
drm.edid_firmware=HDMI-A-1:edid/1280x720.bin
firmware_class.path=/run/pocketfed-fw
rd.smoo.max_io=16384
pocketfed.liveboot=<unique-trial-marker>
```

Whitespace is normalized by `bundle`. The initrd must provide the EDID, zram,
matching USB/ublk/display modules and switch-root storage support. Keep the
16 KiB I/O limit for this kernel's USB path. `enforcing=0` is the existing lab
recipe's SELinux workaround, not an assertion of enforcing-mode support.
Remove the old recipe's `root=`, `rd.smoo.root=`, `rd.smoo=`, and duplicate
transport/COW-enable arguments; fastboop supplies these. The trial's final
command line stayed below 511 bytes, also avoiding the known truncation limit
of the older resident. Its debug/reboot options were not carried over.

From `tools/liveboot`, with the board already in U-Boot fastboot:

```sh
fastboot -s "$TARGET_SERIAL" getvar product  # must report sbc
fastboot -s "$TARGET_SERIAL" getvar serialno

target/release/pocketfed-liveboot bundle \
  --root-image "$DB410C_ROOT_IMAGE" \
  --kernel "$DB410C_KERNEL_BUNDLE/Image.gz" \
  --initrd "$DB410C_INITRD" \
  --dtb "$DB410C_KERNEL_BUNDLE/qcom/apq8016-sbc.dtb" \
  --device-profile profiles/uboot-db410c.yaml \
  --serial "$TARGET_SERIAL" --cmdline-file cmdline.txt --out trial

target/release/pocketfed-liveboot image trial --output trial.img
target/release/pocketfed-liveboot boot trial --wait 30
```

Record UART at 115200 8N1 throughout. Leave the boot process running while the
guest uses its USB root; shut down the guest before stopping it. A user service
can keep the host process independent of an interactive terminal. Use the same
cache configuration for `image` and `boot` when comparing generated export IDs:
the pinned fastboop/gibblox graph's source identity can change with the reader's
cache wrapper. The live command line and runtime export are derived together;
do not copy an ID from an earlier `image` invocation into the recipe.

## Hardware result, September 22, 2026

Consumer commit `e0427584`, fastboop Git `1e6d64b3`, smoo crates `0.0.2-rc.7`:

- Fastboop detected the exact requested serial, downloaded and RAM-booted the
  45,379,584-byte payload directly through U-Boot, then served the root itself.
  No standalone smoo-host or Pocketboot resident was used.
- Fedora 46 reached serial root autologin, with the trial marker in
  `/proc/cmdline`, the expected kernel, and CPUs `0-3` online.
- `phrog` was active, HDMI reported connected, and the user confirmed the
  greeter was visible on the monitor.
- `/sysroot` used `/dev/mapper/smoo-root`; its dm table was an 8 GiB snapshot
  over ublk with a 512 MiB RAM COW device. The storage process survived
  switch-root in `smoo-root-storage.service`. Zram swap was active (874 MiB).
- A 1 MiB file written and synced under `/var/lib` was visible in the guest's
  snapshot and absent from the backing image. The complete backing image's
  SHA-256 remained unchanged after boot and after this explicit write.

This validates one direct-U-Boot boot and the storage handoff/COW contract.
It does not validate Sargo shim hardware, installation, cold-boot automation,
reconnects, multi-device discovery, or GPU stability. Existing Sargo-specific
`usb-signaller`/`81voltd` service failures were present in the reused root;
they did not prevent the greeter or storage handoff. Image preparation and
device recipe consolidation remain separate work.
